# 自动节拍识别审查与技术路线

日期：2026-10-11。范围：当前源码静态审查及上游官方资料核对；未修改实现、未运行音频评测，因此不能声称某首实际音频的误差或新模型的改善比例。

## 现有链路

导入 WAV 先压 MP3 → 解码 → 选最长一条分轨 → 声道算术平均 → 块平均降采样 → 全频谱正向差分包络 → 全局 90 分位峰 → 55–200 BPM 相位聚拢搜索 → 用谱面节奏型、谱面速度和长度比重选 BPM/原点 → 等间距网格。

自动端只生成恒定速度；TempoMap 已有 curve 能力，但波形拍线与吸附仍使用 gridBpm/gridPhase 的恒定网格。检测节拍、检测小节第一拍、将谱面起点对应到音频，是三个不同的问题。

## 发现与优先级

### P1：长度比不能作为倍速的硬证据

beat.ts 的 fits/spanChosen 优先选择谱面时长接近剩余音频时长的候选。若谱只记半首，正确 BPM 会呈现约 0.5 的比例，半速错误候选反而接近 1。省略前奏、反复未展开、间奏与尾奏同样破坏假设。totalScoreBeats 直接统计存储事件，未展开演奏反复。

matchOrigin 失败后只要有 scoreBeats 就放宽匹配；最终 `pick.score > 0 || totalScoreBeats` 可采纳负匹配分数。UI 还会依据 spanRatio 更新谱面 BPM。这会将不可靠猜测写成后续先验。

建议：长度只做弱证据；没有明确“完整转录”条件不据此定倍速；保留半速/原速/倍速候选；节拍估计与谱面起点匹配分开判断，未确认的估计不自动覆盖谱面速度。

### P1：可信度门槛不足以排除错误

beat.ts residual 只累计距离小于 1/4 拍的峰，其余被排除。因此 residualMs 是“命中峰残差”，并非所有峰的整体误差。UI usable 是原点存在、hitRatio≥0.2、confidence≥0.15 三者任一满足。若峰相位均匀分布，落在 ±1/4 拍的比例理论上约 0.5，0.2 不是有效的随机基线排除条件。

建议：报告命中率、全体距离分布、候选差距与分段稳定性；匹配原点存在不等于可信；避免将 R 显示为准确率。

### P1：输入轨道选错的风险

EditorApp.runAutoAlign 与 onAudioPicked 选最长轨道，等长保留第一条。并未优先鼓轨，也未融合多个轨道；上传顺序会影响选择。mixdown 是波形算术平均，注释所说“能量平均”不准确；相位相反的左右声道可能相消。

建议：显式区分鼓/伴奏/人声，可自动比较各轨节奏证据。传统起音检测优先鼓或打击乐成分，但整曲训练的神经模型也应同时评估原始伴奏，不保证纯鼓永远更好。按声道计算特征后融合可避免波形相消。

### P1：重新识别结果可能未进入实际播放

runAutoAlign 更新 tempoDraft，但不清 tempoOverride。audioTempo 在锚点不足 2 个时优先返回 override；若原点未匹配成功，旧锚点也保留。因此可能出现界面 BPM 已改变、实际播放仍走旧曲线，或旧音频拍索引被新 BPM 解释。

建议：明确自动重识别与已有人工曲线/锚点的替换规则；人工结果优先保留时，应显示自动结果仅供参考，不显示成已应用。

### P2：包络时间索引存在一帧差

onsetEnvelope 将第 f 帧差分写入 env[f-1]，但返回 t0Sec=N/(2*sr)。若按当前注释所定义的帧中心时间，应是 (HOP+N/2)/sr；当前少了 HOP/sr，在 11025 Hz 下约 23.2 ms。频谱差分对不同 attack 还有额外偏差，因此修正索引不等于所有音乐起音都会达到同一精度。

### P2：固定 BPM 模式仍可能被精化改变

fixedBpm 跳过初次 BPM 搜索，但后续 pick 为正且未被长度比定案时仍进入 around 附近的 evalAt 精化。按钮语义“按谱面速度对齐”没有在后半流程严格锁住 BPM。

### P2：算法的适用边界

- 全局 90 分位阈值易遗漏柔和前奏/弱鼓；全部频率峰会混入旋律、和弦与切分。
- 初始 BPM/相位仅分析前 150 秒；原点模板也只能在该包络覆盖范围内匹配。
- 分段检测仅搜初值 ±2 BPM，并对 BPM 列表截尾，可能掩盖较大或局部变速；只提示变速，没有自动生成非等间距拍点。
- 窗中心、差分峰、真实音乐拍感不完全等价；块平均降采样只有有限抗混叠能力。
- 波形 grid/吸附使用恒定时轴，即使播放器已有曲线也不会显示真实变速拍点。
- 6/8 等复拍子的听感拍与内部四分音符 tick 基准需明确转换，不能只在 1/2/2 倍之间猜测。

## 可选技术路线

| 路线 | 适用与优势 | 代价与边界 |
|---|---|---|
| A 修正现有算法，加多频带/局部阈值/候选与动态规划 | 保留纯浏览器、包小、无模型；恒速流行伴奏可改善 | 弱节奏/切分/自由速度仍困难，不宜承诺通用高精度 |
| B Beat This! 本地离线推理 | 直接输出 beat/downbeat；官方代码和权重 MIT；主模型约 78 MB，小模型约 8.1 MB | Python/PyTorch 及运行时增加部署成本；CPU 速度需实测；分离音频、无鼓音乐仍可能错 |
| C Beat This! 模型转 ONNX，浏览器 WASM/WebGPU | 同类逐拍模型，离线运行、不用外部服务 | 官方 Python 实现不能直接当浏览器插件；需验证算子、特征、重采样、分段边界与数值一致性；开发成本最高 |
| D librosa 动态规划/PLP，或移植同类算法 | 无大型模型，可提供时间变化 BPM；适合传统算法升级与对照 | librosa 是 Python；浏览器需移植/其他实现；复杂弱节奏表现需评估 |
| E BeatNet 或 madmom RNN+DBN | 节拍/小节首拍跟踪；BeatNet 有实时与离线模式 | 实时能力对整曲导入收益有限；依赖部署更繁杂；madmom 模型为非商业许可，需要单独评估 |
| F Essentia 多特征拍点提取 | 输出拍点、BPM 和置信度，可走 C++ 实现 | RhythmExtractor2013 输入要求 44100 Hz；弱节奏需实测，发行方案需核对官方许可 |

上表的准确率排序是工程选型判断，不是本项目音频评测结论。保留原始伴奏用于模型分析；分轨为可选辅助，勿先假定某轨一定更准确。

## 推荐

短期先修 P1 问题，保留现有算法作为快速初估。若愿意增加本地分析组件，优先 B；若必须保持纯浏览器，先 A，再验证 C。D 是传统算法对照；E/F 不是本项目当前的首选。

统一新输出为 beatTimes + downbeatTimes + 诊断证据，并接入 TempoMap.curve、波形显示、吸附、播放和导出。恒速且逐拍残差足够小时，再拟合为 constant。谱面起点另行匹配/人工确认。

现有手动打拍保留；可将用户一小段打拍作为节拍层级与起点约束，让自动模型继续分析其余音频。对无法确认的片段标示需要校正，不通过等间距外推伪装成已准确识别。

后续验收应使用用户实际错误音频及人工标注，覆盖恒速、倍速歧义、弱鼓、变速、复拍子、长前奏和不完整谱面，分别统计拍点遗漏/多检、倍速错误、首拍偏移、前中后漂移和人工修正量。
