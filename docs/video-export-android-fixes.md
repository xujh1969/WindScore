# 视频导出优化与 Android 白屏修复

2026-10-19，基于当前工作区 0.2.76；保留了原有未提交改动。

## Android 白屏原因

原始 `WindScore-android-0.2.76.apk` 中，`assets/library.html` 引用 `/assets/main-rfloB_uL.js`。
页面入口是 `https://appassets.androidplatform.net/assets/library.html`，资源加载器会去掉 URL 的 `/assets/` 前缀，
所以实际请求 APK 内的 `assets/main-rfloB_uL.js`。该文件不存在，真实文件位于 `assets/assets/main-rfloB_uL.js`。
React 启动脚本加载失败，页面只剩空的 `#root`。

修复：Android 专用 Vite 模式使用相对路径，输出到 `dist-android`；Gradle 打包前自动构建并同步到生成资源目录。
`scripts/check-android-assets.mjs` 按资源加载器规则检查所有 HTML 的 JS/CSS 路径，失败时停止打包。
同时修复 WebView 状态恢复失败时没有加载入口页的问题。

## 视频导出优化

- 按可见范围绘制，边界计算缓存到当前排版对象；保留整组声部和额外墨迹范围。
- 简谱静止视口缓存静态画面，重画活动声部区域；连续滚动时直接绘制，避免每帧重建缓存。
- 五线谱保留可见范围内的矢量绘制，避免局部栅格缓存造成曲线/字形抗锯齿差异。
- 每次导出只分组一次声部时间线，减少每帧重复分组。
- 修正编码探测的 `frameRate` 参数，并向视频轨声明实际帧率。
- 探测硬件偏好配置是否受支持，支持时请求硬件编码；这仍是运行环境可以忽略的提示。
- MP4 关闭内存式 Fast Start，减少媒体数据重复驻留和集中收尾。代价是元数据位于文件尾，网络渐进播放需要先取得尾部元数据；本地完整文件播放不受此限制。
- base64 转换改用原生异步 FileReader，Rust 解码与写盘移到阻塞工作线程。
- 导出进度不再提前到 100%，增加阶段提示，以及混音、绘制、编码等待、封装、base64、IPC/写盘的控制台计时。

- 原优化配置完成 367.27 秒、1920×1080、30fps、11,018 帧的带声 MP4，耗时约 132 秒；因此离线绘制提速和独立编码结果均不能解释主程序里的严重卡顿。
- 当前交付版恢复自动选择编码器、直接绘制和默认 MP4 Fast Start，移除帧循环中额外的定时器让步；保留可见范围裁剪、预先分组及异步分块写盘。栅格缓存不再用于生产导出。
- 回退配置在同一独立进程测试中完成整段编码约 157 秒。该次测试与发布编译并行，不能据此比较两个配置的速度；两次测试都跳过最终保存对话框与写盘。
- 界面每秒显示帧速、绘制/编码平均耗时和帧数；发布 EXE 自动记录实际配置、音频准备、逐秒耗时、取消/完成/错误。
- 日志由 Tauri 的 `app_log_dir()` 保存。Windows 位置为 `%APPDATA%\com.ayou.windscore\logs\video-export-latest.jsonl`，每次导出覆盖上次记录。

## 2026-10-20：主程序日志确认瓶颈，增加实测速率选择

用户运行诊断版后，`video-export-latest.jsonl` 记录：1920×1080、30fps、11,018 帧，窗口持续可见，1341 帧后取消。绘制累计 1782ms（约 1.33ms/帧），CanvasSource.add 累计等待 179075ms（约 133.54ms/帧）；音频编码 2863ms。实际约 7.4 帧/秒，绘制和 add 两项耗时中超过 99% 位于 add 链路。该链路同时包含画布取帧和编码背压，尚不能仅凭这份日志断言具体 GPU/驱动原因。

`WindScore-0.2.76-export-adaptive-v3.exe` / 同名 MSI：

- 将原 CanvasSource 的取帧和送编码器两步显式拆开，分别记录 captureMs 与 encodeWaitMs；样本在每帧 finally 中关闭。
- 在实际主程序、实际画布上短测最多 24 帧；默认路径已快于实时速度时直接使用。默认路径慢于实时速度时，再试软件编码，软件实测耗时至少低 25% 才切换。
- 保持原视频分辨率、帧率、码率、画面及声音。每次导出重新测量，不持久化机器相关选择。
- 短测配置、耗时及最终选择写入同一自动日志；短测失败不强制切换，取消会释放测试输出。

TypeScript 检查、导出计算回归、原生 WebView2 中“模拟默认编码卡顿后自动选择软件并生成 60 帧 MP4”和短测取消回归已通过。新版独立测试还完成《息夫人》11,018 帧的带声 MP4 编码流程，约 116 秒，仍替代了最终保存步骤。是否解决用户主程序中的具体慢路径，仍需此 EXE 的实际导出日志确认，不能用独立测试进程的帧速作保证。

## 2026-10-20：确认对轨页波形持续重绘导致编码变慢

v3 主程序日志进一步排除了取帧：530 帧中 captureMs 仅 273ms（约 0.52ms/帧），编码等待为 74581ms。默认和软件短测分别约 3642ms / 3446ms，切换编码偏好不能解决问题。

用户确认是在对轨页导出。代码中 AudioWaveform 无条件运行 requestAnimationFrame，即使停止播放、被导出弹窗覆盖也持续重绘；导出遮罩使用 backdrop-filter。随后用同一 EXE、同一文件和参数改从演奏页导出，主程序日志记录 5712 帧、视频阶段约 73.5 秒，即约 78 帧/秒；对轨页约 7 帧/秒。

原生复现也验证了这个差异：在独立进程中挂载真实 AudioWaveform 后，24 帧短测约 5.8 秒；在同一进程移除波形后，默认编码短测降至约 0.87 秒。波形回调的 JavaScript CPU 时间很少，不能把之前的 add 等待简单解释为 H.264 计算耗时；持续画布刷新与编码并行造成了此处可复现的性能问题。

v4 的实际修复仅给 AudioWaveform 增加 paused 参数，EditorApp 在 exportOpen 时暂停其动画循环。React effect 清理会取消已排队的帧；关闭弹窗后恢复。删除 v3 中未解决问题的编码短测逻辑，保留默认编码选择和取帧/编码日志。交付为 `WindScore-0.2.76-export-fixed-v4.exe` 及同名 MSI。

最终验证：`scripts/video-waveform-probe.tsx` 在同一原生进程中挂载真实波形，先复现未暂停时的卡顿，再保持组件挂载并设置 paused。完整 367.27 秒、11,018 帧、带声 MP4 编码流程约 146.8 秒完成（最终保存对话框/写盘仍由测试替代）；暂停期间 requestAnimationFrame 回调计数保持 83，恢复后增加至 90。TypeScript、现有导出回归、Windows EXE/MSI 发布构建均通过。
